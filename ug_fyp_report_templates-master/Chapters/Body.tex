\chapter{Requirements}
\section{Brief}
This chapter defines the requirements for the WhatsApp-like prototype developed in this dissertation. Drawing on the literature review, it identifies the relevant stakeholders, use cases, functional and non-functional requirements for the prototype.
\section{Stakeholders}

\begin{enumerate}
  \item \textbf{Photo Sender:}
  The sender shares the photo and configures its permissions. This stakeholder requires clear pre-send and post-send controls, visibility over the current state of a shared photo, and interaction patterns that allow revocation or permission change without unnecessary confusion.

  \item \textbf{Recipient:}
  The primary recipient receives the sender's photo in the original chat. This stakeholder requires clear feedback about whether a photo remains visible, or whether any kind of revocation action has been taken.

  \item \textbf{Secondary Recipient:}
  The secondary recipient appears only when the primary recipient forwards a photo. This stakeholder is necessary because the prototype examines whether sender-defined permissions continue to shape access after redistribution within the platform model.
 
  \item \textbf{Co-Subject:}
  The co-subject is a person depicted in a photo. This stakeholder is necessary because the prototype examines whether co-subjects can request changes to the photo's permissions.
\end{enumerate}

\section{Use Case Scenarios}

\textbf{(UC-S0): Sender Configures Permissions Before Sending}
\begin{enumerate}
    \item The sender opens a chat and selects or uploads a photo.
    \item The sender prepares the photo for sharing by configuring forwarding, view-once, downloading, expiry and co-subject declaration.
    \item The sender sends the photo into the chat.
    \item The photo appears in the conversation with the chosen permission state applied.
\end{enumerate}

\textbf{(UC-S1): Sender Revises Permissions After Sending}
\begin{enumerate}
    \item The sender clicks the photo options button in the top corner of the shared photo message.
    \item The sender selects 'Revocation permissions' from the in-chat action menu.
    \item The system displays the available permission controls in the same in-chat menu.
    \item The sender revises one or more permissions (e.g.\ revoking or restoring access, allowing or blocking forwarding and downloading, or setting, changing, or removing a time limit).
    \item The system updates the photo state in the relevant stakeholder's chat.

\end{enumerate}

\textbf{(UC-R1): Primary Recipient Encounters Active, Revoked, or View-Once Access}
\begin{enumerate}
    \item The primary recipient views the photo's current state in the chat interface.
    \item The system presents the photo according to its current permission state, so that the recipient either sees the photo, opens it as view-once content, or is informed that access is no longer available.
    \item The recipient may open the photo options menu and acts within the limits of the available permissions, such as replying, forwarding, downloading, or requesting access.
\end{enumerate}

\textbf{(UC-R2): Primary Recipient Forwards an Allowed Photo}
\begin{enumerate}
    \item The recipient attempts to forward the photo.
    \item The system checks whether forwarding is currently permitted by the sender's settings.
    \begin{itemize}
        \item If forwarding is allowed, the forwarding option remains available.
        \item If forwarding is not allowed, the forwarding path is blocked.
    \end{itemize}
    \item The photo is forwarded with the sender-defined constraints preserved in the prototype model.
\end{enumerate}

\textbf{(UC-SR1): Secondary Recipient Receives Constrained Forwarded Content}
\begin{enumerate}
  \item The secondary recipient receives the photo in a separate forwarded chat after the primary recipient forwards it.
  \item The system displays the forwarded photo using the original sender's current permission state.
  \item The secondary recipient views the forwarded content through the interface.
  \item The secondary recipient can interact with the photo only within the inherited constraints.
  \item If the sender later revokes access or the photo expires, the forwarded content also becomes unavailable in the secondary recipient's chat.
\end{enumerate}

\textbf{(UC-C1): Co-Subject Requests Revocation of a Shared Photo}
\begin{enumerate}
    \item The co-subject opens their view of the chat containing a photo in which they are depicted.
    \item The system informs that the co-subject appears in the shared photo.
    \item The co-subject opens the photo or views its current access state through the interface.
    \item The co-subject opens the photo options menu from the button in the top corner of the photo message.
    \item The co-subject selects 'Request revocation' and may add an optional explanation.
    \item The system sends the revocation request to the sender for review and response.
\end{enumerate}

FR12 &
The prototype must support multi-party photos by letting senders mark photos containing others and letting depicted co-subjects request revocation, optionally with an explanation.&
Supports multi-party privacy by recognising that shared photos affect depicted co-subjects as well as senders, so disclosure decisions involve shared privacy stakes and co-subjects should have agency to renegotiate disclosure. \cite{cherubini_2021, bourgeus_vandercruysse_2024,xu_my_2017, petronio_cpm_2020,nissenbaum_contextual_2011} &

FR13 &
The prototype should notify depicted co-subjects that they appear in a shared photo when the sender marks it as multi-party content. &
Supports co-subject awareness by making it visible when a privacy-relevant disclosure involves them. It is consistent with literature emphasising that awareness is a necessary precondition for agency. \cite{cherubini_2021, liu_privacy_2023, xu_my_2017, bourgeus_vandercruysse_2024} &
RG3
\\ \hline

FR14 &
The prototype should allow the sender to review and respond to a co-subject’s request through a dedicated decision interface. &
It supports multi-party privacy as a negotiated process by allowing the sender to explicitly review and respond to co-subject requests, reflecting the literature’s view that privacy is collaborative and consent is revisable through stakeholder negotiation. \cite{cherubini_2021, xu_my_2017, xu_trust-based_2019, petronio_cpm_2020, im_yes_2021} &
RG3

RG3

RG3
