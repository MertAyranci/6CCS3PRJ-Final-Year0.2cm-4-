\chapter{Requirements}
\section{Brief}
This chapter defines the requirements for the WhatsApp-like prototype developed in this dissertation. Drawing on the literature review, it identifies the relevant stakeholders, use cases, functional requirements, and non-functional requirements for a prototype centred on photo permissions and revocation. The implemented scope includes pre-send and post-send permission configuration, recipient understanding of changing access states, constrained forwarding to a secondary recipient, and co-subject-related features within the current prototype. Together, these requirements translate the dissertation’s broader privacy and consent concerns into a structured and implementable system specification. (buna da bak->>) Broader issues that remain beyond the present prototype scope are identified separately as deferred concerns.
\section{Stakeholders}

\begin{enumerate}
  \item \textbf{Photo Sender:}
  The sender shares the photo and configures its permissions. This stakeholder requires clear pre-send and post-send controls, visibility over the current state of a shared photo, and interaction patterns that allow revocation or permission change without unnecessary confusion.

  \item \textbf{Primary Recipient:}
  The primary recipient receives the sender's photo in the original chat. This stakeholder requires clear feedback about whether a photo remains visible, or whether any kind of revocation action has been taken.

  \item \textbf{Secondary Recipient:}
  The secondary recipient appears only when the primary recipient forwards a photo. This stakeholder is necessary because the prototype examines whether sender-defined permissions continue to shape access after redistribution within the platform model.
 
  \item \textbf{Co-Subject:}
  The co-subject is a person depicted in a photo. This stakeholder is necessary because the prototype examines whether co-subjects can request changes to the photo's permissions.
\end{enumerate}

\section{Use Cases}

\textbf{(UC-S0): Sender Configures Permissions Before Sending}
\begin{enumerate}
    \item The sender opens a chat and selects or uploads a photo.
    \item The sender prepares the photo for sharing by configuring the following settings:
    \begin{itemize}
        \item Forwaring permission
        \item View once permission
        \item Download permission
        \item Expiry Permission
        \item Co-subject declaration
    \end{itemize}
    \item The sender sends the photo into the chat.
    \item The photo appears in the conversation with the chosen permission state applied.
\end{enumerate}

\textbf{(UC-S1): Sender Revises Permissions After Sending}
\begin{enumerate}
    \item The sender returns to a chat containing a previously shared photo.
    \item The sender clicks the photo options button in the top-right corner of the photo message.
    \item The sender selects 'Revocation permissions' from the in-chat action menu.
    \item The system displays the available permission controls in the same in-chat menu.
    \item The sender revises one or more permissions.
    \begin{itemize}
        \item The sender revokes or restores photo access.
        \item The sender allows or blocks forwarding.
        \item The sender allows or blocks downloading.
        \item The sender sets, changes, or removes a time limit.
    \end{itemize}
    \item The system updates the photo state in the chat.
    \item The sender and other relevant participants see the revised access state.
\end{enumerate}

\textbf{(UC-R1): Primary Recipient Encounters Active, Revoked, or View-Once Access}
\begin{enumerate}
    \item The primary recipient opens the chat containing the sender's photo.
    \item The recipient views the photo's current state in the chat interface.
    \item The system presents the photo according to its current permission state, so that the recipient either sees the photo, opens it as view-once content, or is informed that access is no longer available.
    \item The recipient may open the photo options menu from the button in the top-right corner of the photo message.
    \item The recipient acts within the limits of the available permissions, such as replying, forwarding, downloading, or requesting access.
\end{enumerate}

\textbf{(UC-R2): Primary Recipient Forwards an Allowed Photo}
\begin{enumerate}
    \item The primary recipient opens a chat containing a received photo.
    \item The recipient attempts to forward the photo.
    \item The system checks whether forwarding is currently permitted by the sender's settings.
    \begin{itemize}
        \item If forwarding is allowed, the forwarding option remains available.
        \item If forwarding is not allowed, the forwarding path is blocked.
    \end{itemize}
    \item The photo is forwarded with the sender-defined constraints preserved in the prototype model.
\end{enumerate}

\textbf{(UC-SR1): Secondary Recipient Receives Constrained Forwarded Content}
\begin{enumerate}
  \item The secondary recipient receives the photo in a separate forwarded chat after the primary recipient forwards it.
  \item The system displays the forwarded photo using the original sender's current permission state.
  \item The secondary recipient views the forwarded content through the interface.
  \item The secondary recipient can interact with the photo only within the inherited constraints.
  \item If the sender later revokes access or the photo expires, the forwarded content also becomes unavailable in the secondary recipient's chat.
\end{enumerate}

\textbf{(UC-C1): Co-Subject Requests Revocation of a Shared Photo}
\begin{enumerate}
    \item The co-subject opens their view of the chat containing a photo in which they are depicted.
    \item The system shows that the co-subject appears in the shared photo.
    \item The co-subject opens the photo or views its current access state through the interface.
    \item The co-subject opens the photo options menu from the button in the top-right corner of the photo message.
    \item The co-subject selects 'Request revocation'.
    \item The co-subject may add an optional message explaining the request.
    \item The system sends the revocation request to the sender for review.
\end{enumerate}

\multicolumn{5}{|l|}{\textbf{Usability}} \\ \hline
NFR1 &
The interface must be easy to understand for first-time users. &
Ensure that users can understand the permission model and core controls immediately without prior training or repeated use. &
First-use interpretability; consent controls should be usable, legible, and consistently presented rather than hidden or ambiguous. \cite{schaub_notice_2015,wilbanks_design_2018,im_yes_2021,albesher_2021,schnitzler_2020,bourgeus_vandercruysse_2024,nouwens_dark_2020} &

\\ \hline

NFR2 &
The system shall support quick completion of routine sharing tasks whilst introducing only proportionate friction for privacy-sensitive actions; enough to support reflection, but not so much that users avoid the feature. &
Balance everyday efficiency with reflective intervention so privacy-sensitive actions receive attention without making the system feel burdensome or disruptive. &
Consent interactions should be unburdensome but reflective: routine actions should stay low-friction, while privacy-sensitive sharing can justify proportionate prompts or warnings that support attention without causing fatigue or avoidance. \cite{im_yes_2021,schaub_notice_2015,wilbanks_design_2018,lindegren_evaluation_2021,cherubini_2021,lee_identifying_2023,baruh_big_2017} &
RG1
\\ \hline

NFR3 &
Consent and privacy controls must present choices in a clear, balanced, and non-manipulative way. &
Ensure users can understand and compare options without hidden choices, unequal emphasis, or pressure toward a preferred action. &
Meaningful consent is undermined by dark patterns, unequal salience, hidden decline paths, and unclear notices; privacy controls should remain interpretable and support freely made choices. \cite{nouwens_dark_2020,bermejo_fernandez_2021,soe_2020,gray_etal_2021,wilbanks_design_2018,schaub_notice_2015} &
RG1 and RG3
\\ \hline

NFR4 &
The interface must provide readable and distinguishable permission states, labels, and controls. &
Make permission-related information easy to read, compare, and interpret so users can recognise states and act confidently. &
Permission states and controls must be visually legible and clearly distinguishable so users can interpret privacy status changes, locate actions, and understand consequences without ambiguity. \cite{schaub_notice_2015,wilbanks_design_2018,im_yes_2021,schnitzler_2020,albesher_2021} &
RG1 and RG2
\\ \hline

\multicolumn{5}{|l|}{\textbf{Performance}} \\ \hline
NFR5 &
Permission-related actions and status changes should remain responsive enough for live demonstration in a local browser environment. &
Preserve a smooth and credible interaction flow by ensuring that permission changes appear promptly during use and evaluation. &
Low-friction interaction is important in fast-paced messaging; consent controls should remain usable at the moment of action and not introduce disruptive delay. \cite{wilbanks_design_2018,im_yes_2021,schaub_notice_2015,lindegren_evaluation_2021,lee_identifying_2023,albesher_2021} &
RG1

NFR6 &
The interface must use neutral, non-blaming language to reduce unnecessary social tension when permissions change. &
Reduce avoidable interpersonal friction by ensuring that permission changes are communicated in a socially careful and non-accusatory way. &
Revocation is a socially meaningful boundary change, so interface wording should minimise blame, ambiguity, and interpersonal friction while keeping changes intelligible. \cite{petronio_cpm_2020,child_petronio_cmc_privacy_2011,schnitzler_2020,daft_lengel_mrt_1986,short_williams_christie_1976,ishii_etal_2019,wilbanks_design_2018,schaub_notice_2015} &

\\ \hline

\multicolumn{5}{|l|}{\textbf{Consistency}} \\ \hline
NFR7 &
Permission menus, indicators, and states should remain consistent with familiar WhatsApp-like interaction patterns. &
Improve learnability and reduce confusion by aligning new permission controls with interaction patterns users already recognise from WhatsApp-like messaging. &
Consistency supports interpretable privacy control: revocation-related settings should follow familiar messaging patterns and avoid inconsistent placement or presentation that makes actions harder to locate or understand. \cite{albesher_2021,schaub_notice_2015,wilbanks_design_2018,im_yes_2021,schnitzler_2020,whatsapp_delete_messages,whatsapp_disappearing_messages,whatsapp_view_once} &
RG1 and RG4

NFR8 &
Permission management should assume continuity with WhatsApp’s existing end-to-end encryption model, without requiring changes to the underlying encryption architecture. &
Preserve conceptual compatibility with users’ expectations of secure WhatsApp-like communication while introducing permission controls. &
This assumption ensures that the proposed permission model is interpreted as operating alongside, rather than replacing or weakening, WhatsApp’s existing end-to-end encryption. It supports consistency by framing permission management as an additional layer of user control that remains compatible with familiar secure messaging expectations. &
RG1 and RG4
\\ \hline

NFR9 &
