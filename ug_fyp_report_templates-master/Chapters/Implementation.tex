\section{Technology Choices and Prototype Scope}\label{sec:tech-choices}

\subsection*{Next.js and React}

React~19 was chosen for its component-based architecture, which supports modular development, reuse across the interface, and manageable UI state \cite{react_docs}. This suited the prototype particularly well, as the sender, recipient, forwarded recipient, and co-subject perspectives could be implemented as distinct interface regions while still sharing a common permission state. React's built-in state hooks allowed permission changes, such as revocation, forwarding restrictions, and time-limit expiry, to propagate immediately across the relevant views, supporting the responsiveness specified by \textbf{NFR5}. Because the prototype operates as a single-browser simulation rather than a networked multi-user system, this behaviour could be implemented without introducing an external state-management library.

Next.js~16 was used as the application framework, providing project scaffolding, routing, TypeScript integration, CSS processing, and an optimised production build pipeline \cite{nextjs_docs}. Although the prototype is essentially a single-page application, Next.js streamlined development and supported rapid iteration across the two implementation rounds described in Section~\ref{sec:dev-process}.

\subsection*{TypeScript}

TypeScript was used to define and enforce the core data structures of the prototype at compile time \cite{typescript_docs}. This was particularly important because the Smart Photos prototype relies on a structured permission model spanning message content, stakeholder roles, and photo-specific control. Several key types were used throughout the implementation:

\begin{itemize}
  \item \texttt{PhotoPermissions} --- encodes revocation status, forwarding, view-once, download, time-limit, and co-subject flags;
  \item \texttt{ChatMessage} --- a discriminated union distinguishing text messages from photo messages, each carrying different metadata;
  \item \texttt{Participant} --- a literal union (\texttt{"sender"}, \texttt{"recipient"}, \texttt{"forwardedRecipient"}, \texttt{"coOwner"}) that restricts handler functions to valid stakeholder roles.
\end{itemize}

\noindent
Using explicit types helped keep these structures consistent across components and reduced the likelihood of development errors as the prototype evolved. This was especially valuable because the permission model is the central contribution of the prototype and any inconsistency in how permissions, messages, or stakeholder roles were represented would have weakened the credibility of the resulting user evaluation. Although TypeScript does not replace runtime permission logic, it improved maintainability and made the implementation safer to extend during iterative refinement.

\subsection*{Tailwind CSS}

Tailwind CSS~4 was chosen as the styling framework because its utility-first approach enabled rapid and consistent interface development without relying on large separate stylesheet files \cite{tailwindcss_docs}. This suited the prototype well, as the interface needed to visually approximate familiar WhatsApp patterns in order to support the familiarity and consistency specified by \textbf{NFR7}. Tailwind's utility classes made it straightforward to replicate these patterns while keeping styling close to the relevant component markup.

The framework was also useful during iterative refinement. Because visual adjustments could be made directly within the JSX, interface details could be revised quickly between implementation rounds without introducing substantial styling overhead. This was particularly valuable in a prototype that underwent multiple rounds of refinement following participant feedback.

\subsection*{Front-End Simulation and Prototype Scope}
The prototype operates entirely as a front-end simulation with in-memory state. Conversation data, permission records, and photo metadata are managed through React state in the browser, with no server, database, or external API. This design was chosen to support the project’s aim of evaluating the interaction design and user experience of consent revocation, rather than the engineering feasibility of a production messaging system. It also allowed multiple perspectives to be demonstrated in a single browser window and made permission changes immediately observable during evaluation.

As such, the prototype is an interactive proof-of-concept for the Smart Photos permission model. It demonstrates revocable consent, permission configuration, forwarding control, view-once behaviour, time-limited access, and co-subject involvement, but does not include production infrastructure such as encryption, authentication, persistent storage, real-time delivery, multi-device synchronisation, automated co-subject detection, or server-side access control.

\subsection*{Testing Tooling}

Vitest was used as the test runner for the prototype because it integrates naturally with the Next.js and TypeScript development environment and supports fast execution of both logic-level and UI-level tests. React Testing Library was used for rendering components and interacting with them through accessible roles, labels, and visible text rather than implementation details. This was appropriate for the Smart Photos prototype because the key question was whether the interface presented the correct permission state and interaction options to users, not whether particular internal variables changed in a specific way. The tests were executed in a jsdom environment, which provided a simulated browser DOM suitable for unit, component, and integration-style testing of the front-end prototype.

\subsection*{Phase 1: Initial Prototype}

The first implementation round focused on realising the core interaction flows defined in the functional specification: pre-send permission configuration (FR1--FR2), post-send permission management including revocation and restoration (FR3, FR5, FR6), recipient-side state presentation (FR4, FR10), constrained forwarding to a secondary recipient (FR7--FR9), access-request and response flows (FR11), and co-subject notification and revocation-request mechanisms (FR12--FR17). Each flow was built as a self-contained interaction path within a single-page React application, with all four stakeholder views rendered side by side so that the consequences of any permission change could be observed across participants in real time.

At this stage the entire prototype resided in a single \texttt{page.tsx} file. This monolithic structure was a pragmatic choice for rapid prototyping. This avoided premature abstraction and kept all state and handlers visible in one place while the interaction model was still being tested and revised. That build was then used for the screenshot-driven interviews reported in Chapter~6.

\subsection*{Evaluation and Rationale for a Second Round}

A second implementation round was justified on methodological rather than evaluative grounds. As Gould and Lewis argue, usability-oriented design is inherently iterative, requiring a system to be modified and tested repeatedly as it develops from simulation to prototype and beyond \cite{gould_lewis_1985}. The design in Chapter~4 was derived from literature and requirements and once a runnable prototype existed, it became possible to observe how people interpreted unfamiliar permission states, warnings, and labels under realistic conditions.

For this project, the interviews therefore functioned as a checkpoint between ``specification-faithful'' code and a version suitable for continued demonstration and assessment. This reflects the role of usability testing in helping designers uncover problems, discover opportunities for improvement, and learn how users actually engage with an interface \cite{moran_usability_testing_101}. A second round was therefore scoped deliberately to layout, styling, copy, and component structure, leaving the core types and permission logic aligned with Chapter~4 unless a change was strictly required for consistency. Chapter~6 documents what was learned from participants and how it was analysed.

\subsection*{Phase 2: Post-Evaluation Refinements}

Phase~2 implemented the interface adjustments motivated by that feedback and, in parallel, restructured the codebase from a single file into a multi-component architecture so that further changes and testing could proceed without entangling unrelated parts of the UI.

\subsubsection*{Architectural Restructuring}
During the second implementation round, the prototype was refactored from a single monolithic file into a modular component structure. The original \texttt{page.tsx} had grown to contain all rendering logic, state management, and UI concerns in one place, making iterative changes increasingly error-prone. Furthermore, this restructuring improved maintainability and made later refinements more manageable. Splitting the codebase allowed interface changes to be applied to individual components without risking unintended side-effects elsewhere, while keeping the underlying permission model separated from presentation concerns. The resulting component hierarchy is described in detail in Section~X.X.

\subsubsection*{Interface Refinements}

Phase~2 focused on improving clarity and prototype fidelity without changing the underlying permission model. Permission information beneath photo messages was condensed into a compact summary with on-demand detail expansion, reducing visual clutter in the chat transcript. The pre-send limitation disclaimer was made more prominent, and the revoked-state placeholder was simplified to reduce repeated explanation. In addition, the prototype was extended to support multi-photo messages with a shared permission set, together with collage and gallery views, bringing the interaction closer to familiar photo-sharing behaviour in mainstream messaging clients. Modal overlays were also scoped to individual handset frames so that each simulated participant view remained visually distinct. Further minor copy and layout adjustments were applied in the same spirit; they are not enumerated here. All these refinements are reflected in the final prototype described in the following sections. 














\section{Components and State Management}\label{sec:components-state}

\subsection*{Component Hierarchy}

The final prototype comprises a thin entry page (\texttt{page.tsx}), a central orchestrator component \newline (\texttt{PhotoRevocationDemo}), and sixteen supporting components organised into five functional groups. Figure~\ref{fig:component-hierarchy} shows the hierarchy schematically and a detailed diagram is provided in Appendix~X.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{figures/component-hierarchy.png}
    \caption{Component hierarchy of the prototype}
    \label{fig:component-hierarchy}
\end{figure}

\texttt{PhotoRevocationDemo} owns all shared application state and passes data and handler functions down to its children as props. Each simulated handset is wrapped in a \texttt{PhoneFrame}, which renders the device chrome and provides a \texttt{ChatPanelOverlayContext} so that overlay components such as \newline \texttt{ViewOnceInChatModal} and \texttt{PhotoStackLightbox} can portal into the correct handset frame rather than covering the entire page. Beneath this shell, the components divide into the following groups:

\begin{itemize}
  \item \textbf{Device chrome.} \texttt{PhoneFrame} renders the handset shell and header for each of the four stakeholder views. It wraps its children in a \texttt{ChatPanelOverlayContext} provider, which exposes a portal target and scroll reference used by overlay components.
  \item \textbf{Conversation rendering.} \texttt{MessageList} iterates over a message array and dispatches each entry to \texttt{TextMessageBubble} or \texttt{PhotoMessageBubble}. Photo messages delegate further to \newline \texttt{PhotoPreview} for single images, \texttt{PhotoStackGrid} for multi-photo collages, and \texttt{PhotoStackLightbox} for full-screen gallery viewing.
  \item \textbf{Composition and configuration.} \texttt{ComposerView} manages the pre-send interface, including caption input and permission toggles. \texttt{PickerSheet} handles photo selection in the sender's footer. Both \texttt{ComposerView} (for the draft time limit) and \texttt{TimeLimitModal} (for post-send adjustment) embed \texttt{ScrollWheelColumn} as a reusable duration picker.
  \item \textbf{Request and modal flows.} \texttt{RequestAccessPanel} and \texttt{RequestRevocationPanel} handle the access-request and co-subject revocation-request interfaces respectively; both are rendered inline in the relevant handset footer. \texttt{ViewOnceInChatModal} manages the view-once confirmation overlay, portalling into the per-handset overlay layer via \texttt{ChatPanelOverlayContext}.
  \item \textbf{Debug and demonstration.} \texttt{PrototypeStateSummary} surfaces the live permission state of the currently selected photo in a panel alongside the handset views, allowing evaluators to verify that permission changes propagate correctly across participants.
\end{itemize}

\noindent
Each group corresponds to a distinct area of the interaction model defined in Chapter~4, so that changes to one concern---such as the composition interface---do not entangle another, such as request handling or message rendering.









\subsection*{Shared Permission State}

All application state that affects what participants see resides in \texttt{PhotoRevocationDemo} as React \texttt{useState} hooks. The most important of these are 5 message arrays (\texttt{mainMessages}, \texttt{forwardedMessages}, \texttt{senderOnlyMessages}, \texttt{recipientOnlyMessages}, \texttt{coSubjectOnlyMessages}) which together hold every message visible across the four simulated handsets.

The canonical permission record for a photo lives on its entry in \texttt{mainMessages}. Figure~\ref{fig:photo-permissions} shows the \texttt{PhotoPermissions} type as implemented in the source (\texttt{types.ts}).

\begin{figure}[H]
  \centering
  \includegraphics[width=0.85\textwidth]{figures/listing-5-1-photo-permissions.png}
  \caption{The \texttt{PhotoPermissions} type (\texttt{types.ts}). Each field maps to a permission control in the sender's configuration panel.}
  \label{fig:photo-permissions}
\end{figure}

Every photo message carries a \texttt{sourcePhotoId} that links it back to the canonical entry in \texttt{mainMessages}. This linking is encoded in the \texttt{ChatMessage} type, which uses a TypeScript discriminated union to distinguish text messages from photo messages. Figure~\ref{fig:chat-message} shows the definition as implemented in the source (\texttt{types.ts}).

\begin{figure}[H]
  \centering
  \includegraphics[width=0.60\textwidth]{figures/listing-5-1-chat-message.png}
  \caption{\texttt{sourcePhotoId} links copies to the canonical record.}
  \label{fig:chat-message}
\end{figure}

When the sender revokes, restores, or otherwise modifies permissions, only the canonical entry in \texttt{mainMessages} is updated. Forwarded copies in \texttt{forwardedMessages} are never rewritten directly. Instead, every rendering component resolves the live permission state at render time by calling \texttt{getEffectivePermissions}, shown in Figure~\ref{fig:get-effective}. This function looks up the canonical photo in \texttt{mainMessages} by matching \texttt{sourcePhotoId}, reads the stored permission fields, normalises \texttt{canDownload} and \texttt{hasCoSubject} with defaults when they are undefined on the stored record, and applies time-limit expiry logic through \texttt{computeEffectiveStatus} before returning the result.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.70\textwidth]{figures/get-effective-permissions.png}
  \caption{Resolving live permissions in \texttt{helpers.ts}}
  \label{fig:get-effective}
\end{figure}

This derivation pattern means that a single state update to the canonical photo in \texttt{mainMessages} is sufficient for every participant view (sender, recipient, forwarded recipient, and co-subject) to reflect the change on the next render cycle. The prototype does not need to synchronise permission records across message arrays or maintain separate update logic for forwarded copies, because every component derives its view of permissions from the same canonical source.

\subsection*{Local Interaction State}

Alongside the shared permission state described above, \texttt{PhotoRevocationDemo} maintains a second category of state: transient values that control temporary interface behaviour rather than the canonical permission model. These include boolean flags that govern which overlay is currently visible (\texttt{pickerOpen}, \texttt{composerOpen}, \texttt{timeLimitModalOpen}), a structured value tracking which photo menu is active and in which mode (\texttt{openPhotoMenu}), and draft text fields that hold in-progress user input before it is committed (\texttt{draftCaption}, \texttt{accessRequestDraft}, \texttt{senderInput}, \texttt{recipientInput}). None of these values affect how permissions are stored or derived and they exist only to support the interactive surface of each handset view.

One notable piece of local state is the countdown tick. The prototype supports time-limited photo access, and the remaining time must update visually every second. Rather than introducing a timer event system, the orchestrator increments a counter once per second via a \texttt{useEffect} hook, as shown in Figure~\ref{fig:countdown-tick}.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.65\textwidth]{figures/countdown-tick-effect.png}
  \caption{Countdown tick effect in \texttt{PhotoRevocationDemo.tsx}. The tick value itself is never read; its sole purpose is to force React re-renders.}
  \label{fig:countdown-tick}
\end{figure}

\noindent
The code intentionally discards the state variable during destructuring, as the underlying tick value remains unused. Its only purpose is to trigger a React re-render every second so that \texttt{getEffectivePermissions} (Figure~\ref{fig:get-effective}) and \texttt{formatExpiryCountdown} re-evaluate with a fresh \texttt{Date.now()}. This allows time-limited photos to expire visually in real time and countdown labels to update continuously, without requiring explicit expiry event handling or additional state-management infrastructure.

Separating these transient interaction values from the canonical permission state kept the implementation manageable. The permission model remained single-source-of-truth structure as described in the previous subsection, while the local state layer provided the flexibility needed to support rich interactions such as modal sequencing, draft composition, and live countdown display.

\subsection*{State Transitions: Revocation and Forwarding}

The two most consequential state transitions in the prototype are post-send revocation and constrained forwarding. Both operate on the canonical--copy architecture described in Section~\ref{sec:components-state}, but they update state in different directions. Revocation modifies the canonical record so that all views change, while forwarding reads the canonical record to decide whether a new copy may be created.

\subsubsection*{Post-Send Revocation}

When the sender revokes access, the handler \texttt{updateSelectedPhotoPermissions} is called with a partial update (for example, \texttt{\{~status:~"revoked"~\}}). This function maps over \texttt{mainMessages}, locates every entry whose \texttt{sourcePhotoId} matches the currently selected photo, and merges the update into its \texttt{permissions} object, as shown in Figure~\ref{fig:update-permissions}.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.85\textwidth]{figures/update-selected-photo-permissions.png}
  \caption{\texttt{updateSelectedPhotoPermissions} in \texttt{PhotoRevocationDemo.tsx}. The immutable map-and-merge pattern updates the canonical record without mutating existing state.}
  \label{fig:update-permissions}
\end{figure}

\noindent
Because \texttt{forwardedMessages} is never rewritten, the revocation takes effect across all participant views through the derivation layer already shown in Figure~\ref{fig:get-effective}. On the next render cycle, every \texttt{PhotoMessageBubble} calls \texttt{getEffectivePermissions}, which looks up the now-revoked canonical record and returns \texttt{"revoked"} as the effective status. The same handler is reused for restoring access, toggling the download flag, or enabling the co-subject flag where each is simply a different partial update passed to the same function.

\subsubsection*{Constrained Forwarding}
Forwarding adds a message to \texttt{forwardedMessages} only after checking the canonical permission state, as shown in Figure~\ref{fig:forward-photo}.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.67\textwidth]{figures/forward-photo-message.png}
  \caption{Forwarding under effective permissions}
  \label{fig:forward-photo}
\end{figure}

Two details are significant. First, the guard clause calls \texttt{getEffectivePermissions} to evaluate the canonical record at the moment of forwarding; if the photo has been revoked or its \texttt{canForward} flag is \texttt{false}, the function returns early and no copy is created. Second, the forwarded message carries the same \texttt{sourcePhotoId} as the original. This means that if the sender later revokes access, the derivation layer will resolve the forwarded copy against the updated canonical record, and the forwarded recipient's view will reflect the revocation without any additional update to \texttt{forwardedMessages}.

\subsubsection*{Time-Limit Expiry}

Time-limited access follows the same derivation principle without requiring a dedicated state transition. When the sender configures a time limit before sending, the photo message is created with an \texttt{expiresAt} timestamp. No handler fires when the deadline passes; instead, \texttt{computeEffectiveStatus} (called within \texttt{getEffectivePermissions}) compares \texttt{expiresAt} against \texttt{Date.now()} on every render and returns \texttt{"revoked"} once the timestamp has elapsed, as shown in Figure~\ref{fig:compute-effective-status}.

\begin{figure}[H]
  \centering
  \includegraphics[width=0.65\textwidth]{figures/compute-effective-status.png}
  \caption{\texttt{computeEffectiveStatus} in \texttt{photoModel.ts}. Expiry is treated as implicit revocation---no event or state write is needed.}
  \label{fig:compute-effective-status}
\end{figure}

\noindent
Combined with the countdown tick described in the previous subsection, this ensures that a time-limited photo transitions smoothly from an active countdown display to a revoked placeholder at the moment of expiry, using The system translates the concept of ongoing and dynamic consent into a tangible feature by using one core function to handle all access rules. Consequently, any single change made at the source (whether by the user or by time expiring) instantly cascades to update all shared copies of the photo.

This two-step flow satisfies the pre-send configuration requirement (\textbf{FR1}) and the risk-cue disclosure requirement (\textbf{FR2}), while the always-visible warning addresses learnability (\textbf{NFR3}) and expectation management (\textbf{NFR9}).

Once a photo has been delivered, the sender retains access to its permission state through contextual controls anchored to the message bubble. Tapping the drop-down overlay on a sent photo opens an actions menu, and selecting \emph{Revocation permissions} transitions to the dedicated submenu shown in Figure~\ref{fig:revoke-menu}. This submenu exposes five post-send controls. \emph{Revoke / Restore photo access}, \emph{Block / Allow forwarding} and \emph{Block / Allow download} govern redistribution, and the remaining two options either remove or assign a time limit. Each menu label reflects the available transition rather than the current value, so the sender always sees what action they can take next.

The result of any change is visible immediately in the chat thread. As shown in Figure~\ref{fig:permission-chips}, each photo message carries a collapsible summary row beneath the bubble. In its compact form, colour-coded tick and cross indicators enable to see the current status at a glance. This post-send surface satisfies the ongoing permission-management requirement (\textbf{FR3}) and the live consent-state requirement (\textbf{FR5}), while the in-chat summary chips address state visibility (\textbf{FR4}) and feedback (\textbf{FR6}).

\subsection*{Forwarding and Access Requests}

When forwarding is permitted and the photo is active, the recipient's action menu enables \emph{Forward}. The forwarded copy carries the same link to the canonical record as the original, which means that any later revocation by the sender propagates to both the recipient and the secondary recipient without additional synchronisation.

The sender's view retains the photo but displays a revoked summary. The both recipient's bubble is replaced by the ``Access changed'' placeholder with permissionsdisabled in the action menu.  At this point the recipient's menu includes \emph{Request access} as the only actionable option beyond \emph{Reply}.

\section{Software Testing}\label{sec:software-testing}

\subsection*{Manual Cross-View Verification}

After each substantive change, the prototype was exercised manually in the browser across all four stakeholder views (sender, recipient, forwarded recipient, and co-subject). These manual checks concentrated on cross-view consistency. They confirmed that when a revocation was made in the sender panel, it was immediately reflected in the recipient and forwarded-recipient panels and that permission chips updated correctly. Manual verification was particularly important for visual and layout details such as colour-coded status indicators, animation transitions, and responsive scaling, that automated tests running in a simulated DOM environment cannot fully capture. Version control was maintained with Git throughout both development phases, providing a traceable history of changes and the ability to isolate regressions.




\subsection*{Automated Unit and Component Tests}

To supplement the manual checks described above, an automated test suite was developed and organised into three layers within a dedicated \texttt{tests/} directory.

\textbf{Unit tests} verify pure helper functions and the permission model in isolation, confirming for example that \texttt{computeEffectiveStatus} treats a past expiry timestamp as revoked regardless of the stored status field and that \texttt{getEffectivePermissions} falls back to a message's own permission record when the canonical source is absent from the main thread.

\textbf{Component tests} render individual UI elements such as the photo bubble, composer, picker, time-limit modal, request panels, and text message bubble within a lightweight harness that supplies controlled props. These tests exercise behavioural branches including a revoked photo displaying the ``Access changed'' placeholder, a view-once photo transitioning to ``Opened once'' after consumption, the download button appearing disabled when \texttt{canDownload} is false, and the co-subject card reflecting both active and revoked states.

\textbf{Integration-style tests} render the full \texttt{PhotoRevocationDemo} orchestrator and simulate multi-step user journeys spanning several handset panels, including revoking a photo and observing the recipient subtitle change, forwarding a photo and verifying its appearance on the secondary handset, accepting or rejecting access and revocation requests, and consuming a view-once photo through the full modal lifecycle.

Edge cases are tested alongside the primary flows, including restoring access on an already-expired time limit (which must also clear the \texttt{expiresAt} field), sending an empty text message, cancelling the time-limit modal without applying an expiry, and verifying that permission-detail chips display the correct label variant depending on whether the underlying policy was view-once. At the time of writing the suite comprises all test cases across 16 test files. Table~\ref{tab:coverage} summarises the coverage collected by \texttt{@vitest/coverage-v8}.

\subsection*{Scope and Limitations of Testing}

The automated suite operates within jsdom, which reproduces DOM structure but does not execute real CSS rendering or browser navigation. No end-to-end framework such as Playwright was introduced, as the additional cost was not justified for a single-page prototype where all views coexist in one render tree. Similarly, because the prototype has no backend, there are no API or database tests. These boundaries are consistent with the project's scope as an interactive prototype. As Myers notes, testing can reveal the presence of defects but never prove their complete absence \cite{myers_2011}. Automated tests serve as a regression safety net for the permission logic and UI behaviour, while the broader question of whether users understand and trust that behaviour is addressed through the qualitative evaluation in Chapter~6. Broader prototype limitations and production considerations are discussed in Section 7.2.
