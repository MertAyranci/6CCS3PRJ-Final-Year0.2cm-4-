\section{Technology Choices and Prototype Scope}\label{sec:tech-choices}

\subsection*{Next.js and React}

React~19 was chosen for its component-based architecture, which supports modular development, reuse across the interface, and manageable UI state \cite{react_docs}. This suited the prototype particularly well, as the sender, recipient, forwarded recipient, and co-subject perspectives could be implemented as distinct interface regions while still sharing a common permission state. React's built-in state hooks allowed permission changes, such as revocation, forwarding restrictions, and time-limit expiry, to propagate immediately across the relevant views, supporting the responsiveness specified by \textbf{NFR5}. Because the prototype operates as a single-browser simulation rather than a networked multi-user system, this behaviour could be implemented without introducing an external state-management library.

Next.js~16 was used as the application framework, providing project scaffolding, routing, TypeScript integration, CSS processing, and an optimised production build pipeline \cite{nextjs_docs}. Although the prototype is essentially a single-page application, Next.js streamlined development and supported rapid iteration across the two implementation rounds described in Section~\ref{sec:dev-process}.

\subsection*{TypeScript}

TypeScript was used to define and enforce the core data structures of the prototype at compile time \cite{typescript_docs}. This was particularly important because the Smart Photos prototype relies on a structured permission model spanning message content, stakeholder roles, and photo-specific control. Several key types were used throughout the implementation:

\begin{itemize}
  \item \texttt{PhotoPermissions} --- encodes revocation status, forwarding, view-once, download, time-limit, and co-subject flags;
  \item \texttt{ChatMessage} --- a discriminated union distinguishing text messages from photo messages, each carrying different metadata;
  \item \texttt{Participant} --- a literal union (\texttt{"sender"}, \texttt{"recipient"}, \texttt{"forwardedRecipient"}, \texttt{"coOwner"}) that restricts handler functions to valid stakeholder roles.
\end{itemize}

\noindent
Using explicit types helped keep these structures consistent across components and reduced the likelihood of development errors as the prototype evolved. This was especially valuable because the permission model is the central contribution of the prototype and any inconsistency in how permissions, messages, or stakeholder roles were represented would have weakened the credibility of the resulting user evaluation. Although TypeScript does not replace runtime permission logic, it improved maintainability and made the implementation safer to extend during iterative refinement.

\subsection*{Tailwind CSS}

Tailwind CSS~4 was chosen as the styling framework because its utility-first approach enabled rapid and consistent interface development without relying on large separate stylesheet files \cite{tailwindcss_docs}. This suited the prototype well, as the interface needed to visually approximate familiar WhatsApp patterns in order to support the familiarity and consistency specified by \textbf{NFR7}. Tailwind's utility classes made it straightforward to replicate these patterns while keeping styling close to the relevant component markup.

The framework was also useful during iterative refinement. Because visual adjustments could be made directly within the JSX, interface details could be revised quickly between implementation rounds without introducing substantial styling overhead. This was particularly valuable in a prototype that underwent multiple rounds of refinement following participant feedback.

\subsection*{Front-End Simulation and Prototype Scope}
The prototype operates entirely as a front-end simulation with in-memory state. Conversation data, permission records, and photo metadata are managed through React state in the browser, with no server, database, or external API. This design was chosen to support the project’s aim of evaluating the interaction design and user experience of consent revocation, rather than the engineering feasibility of a production messaging system. It also allowed multiple perspectives to be demonstrated in a single browser window and made permission changes immediately observable during evaluation.

As such, the prototype is an interactive proof-of-concept for the Smart Photos permission model. It demonstrates revocable consent, permission configuration, forwarding control, view-once behaviour, time-limited access, and co-subject involvement, but does not include production infrastructure such as encryption, authentication, persistent storage, real-time delivery, multi-device synchronisation, automated co-subject detection, or server-side access control.

\subsection*{Phase 1: Initial Prototype}

The first implementation round focused on realising the core interaction flows defined in the functional specification: pre-send permission configuration (FR1--FR2), post-send permission management including revocation and restoration (FR3, FR5, FR6), recipient-side state presentation (FR4, FR10), constrained forwarding to a secondary recipient (FR7--FR9), access-request and response flows (FR11), and co-subject notification and revocation-request mechanisms (FR12--FR17). Each flow was built as a self-contained interaction path within a single-page React application, with all four stakeholder views rendered side by side so that the consequences of any permission change could be observed across participants in real time.

At this stage the entire prototype resided in a single \texttt{page.tsx} file. This monolithic structure was a pragmatic choice for rapid prototyping. This avoided premature abstraction and kept all state and handlers visible in one place while the interaction model was still being tested and revised. That build was then used for the screenshot-driven interviews reported in Chapter~6.

\subsection*{Evaluation and Rationale for a Second Round}

A second implementation round was justified on methodological rather than evaluative grounds. As Gould and Lewis argue, usability-oriented design is inherently iterative, requiring a system to be modified and tested repeatedly as it develops from simulation to prototype and beyond \cite{gould_lewis_1985}. The design in Chapter~4 was derived from literature and requirements and once a runnable prototype existed, it became possible to observe how people interpreted unfamiliar permission states, warnings, and labels under realistic conditions.

For this project, the interviews therefore functioned as a checkpoint between ``specification-faithful'' code and a version suitable for continued demonstration and assessment. This reflects the role of usability testing in helping designers uncover problems, discover opportunities for improvement, and learn how users actually engage with an interface \cite{moran_usability_testing_101}. A second round was therefore scoped deliberately to layout, styling, copy, and component structure, leaving the core types and permission logic aligned with Chapter~4 unless a change was strictly required for consistency. Chapter~6 documents what was learned from participants and how it was analysed.

\subsection*{Phase 2: Post-Evaluation Refinements}

Phase~2 implemented the interface adjustments motivated by that feedback and, in parallel, restructured the codebase from a single file into a multi-component architecture so that further changes and testing could proceed without entangling unrelated parts of the UI.

\subsubsection*{Architectural Restructuring}
During the second implementation round, the prototype was refactored from a single large \texttt{page.tsx} file into a modular structure. The top-level page retained responsibility for coordinating the overall multi-view simulation, while dedicated components under \path{components/photo-revocation-demo} handled specific interface elements such as composition, message rendering, previews, request panels, and modal interactions. Shared definitions and reusable logic were moved under \texttt{src/lib}, including the demo-specific modules in \path{photo-revocation-demo} (\texttt{types.ts}, \texttt{helpers.ts}, and \texttt{initialState.ts}) and the shared \texttt{photoModel.ts} file.

This restructuring improved maintainability and made later refinements more manageable. Interface changes could be applied to individual components without repeatedly modifying one monolithic file, while the underlying permission model remained separated from presentation concerns.

\section{Components and State Management}\label{sec:components-state}

\subsection*{Component Hierarchy (burda sanirim bir yanlis var ai ile check et diagrami)}

The final prototype comprises a thin entry page (\texttt{page.tsx}), a central orchestrator component (\texttt{PhotoRevocationDemo}), and seventeen leaf components organised into four functional groups. Figure~\ref{fig:component-hierarchy} shows this hierarchy.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{figures/component-hierarchy.pdf}
    \caption{Component hierarchy of the prototype, showing the four functional groups.}
    \label{fig:component-hierarchy}
\end{figure}

\texttt{PhotoRevocationDemo} owns all shared application state and passes data and handler functions down to its children as props. Each simulated handset is wrapped in a \texttt{PhoneFrame}, which renders the device chrome and provides a \texttt{ChatPanelOverlayContext} so that modal overlays such as request panels and view-once confirmations can portal into the correct handset frame rather than covering the entire page. Beneath this shell, the components divide into four groups:


\begin{itemize}
  \item \textbf{Conversation rendering.} \texttt{MessageList} iterates over a message array and dispatches each entry to \texttt{TextMessageBubble} or \texttt{PhotoMessageBubble}. Photo messages delegate further to \texttt{PhotoPreview} for single images, \texttt{PhotoStackGrid} for multi-photo collages, and \texttt{PhotoStackLightbox} for full-screen gallery viewing.
  \item \textbf{Composition and configuration.} \texttt{ComposerView} manages the pre-send interface, including caption input and permission toggles. \texttt{PickerSheet} handles photo selection, while \texttt{TimeLimitModal} and its child \texttt{ScrollWheelColumn} provide the time-limit picker.
  \item \textbf{Request and modal flows.} \texttt{RequestAccessPanel} and \texttt{RequestRevocationPanel} handle the access-request and co-subject revocation-request interfaces respectively. Furthermore, \texttt{ViewOnceInChatModal} manages the view-once confirmation overlay, with \texttt{ViewOnceSingleTick} rendering the single-view indicator on consumed messages.
  \item \textbf{Debug and demonstration.} \texttt{PrototypeStateSummary} surfaces the live permission state of the currently selected photo in a panel alongside the handset views, allowing evaluators to verify that permission changes propagate correctly across participants.
\end{itemize}

\noindent
Each group corresponds to a distinct area of the interaction model defined in Chapter~4, so that changes to one concern---such as the composition interface---do not entangle another, such as request handling or message rendering.









\subsection*{Shared Permission State}

All application state that affects what participants see resides in \texttt{PhotoRevocationDemo} as React \texttt{useState} hooks. The most important of these are five message arrays (\texttt{mainMessages}, \texttt{forwardedMessages}, \texttt{senderOnlyMessages}, \texttt{recipientOnlyMessages}, \texttt{coSubjectOnlyMessages}) which together hold every message visible across the four simulated handsets.

The canonical permission record for a photo lives on its entry in \texttt{mainMessages}. Section~\ref{sec:tech-choices} introduced the \texttt{PhotoPermissions} type in prose; Listing~\ref{lst:photo-permissions} shows the definition as it appears in the source:

\begin{lstlisting}[
  caption={The \texttt{PhotoPermissions} type (\texttt{types.ts}). Each field maps to a permission control in the sender's configuration panel.},
  label={lst:photo-permissions},
  language={}
]
export type PhotoPermissions = {
  status: PermissionStatus;     
  canForward: boolean;
  viewOnce: boolean;
  expiresAt: number | null;    
  canDownload: boolean;
  hasCoSubject: boolean;
};
\end{lstlisting}

Every photo message carries a \texttt{sourcePhotoId} that links it back to the canonical entry in \texttt{mainMessages}. This linking is encoded in the \texttt{ChatMessage} type, which uses a TypeScript discriminated union to distinguish text messages from photo messages:

\begin{lstlisting}[
  caption={Photo branch of the \texttt{ChatMessage} discriminated union (\texttt{types.ts}). The \texttt{sourcePhotoId} field links every copy (including forwarded ones) to the canonical permission record.},
  label={lst:chat-message},
  language={}
]
export type ChatMessage =
  | { id: number; sender: Participant; type: "text";
      text: string; time: string;
      /* ...request metadata fields... */ }
  | { id: number; sender: Participant; type: "photo";
      assets: PhotoAsset[];
      caption: string; time: string;
      permissions: PhotoPermissions;
      sourcePhotoId: number; };
\end{lstlisting}

When the sender revokes, restores, or otherwise modifies permissions, only the canonical entry in \texttt{mainMessages} is updated. Forwarded copies in \texttt{forwardedMessages} are never rewritten directly. Instead, every rendering component resolves the live permission state at render time by calling \texttt{getEffectivePermissions}, shown in Listing~\ref{lst:get-effective}. This function looks up the canonical photo in \texttt{mainMessages} by matching \texttt{sourcePhotoId}, reads the stored permission fields, and applies time-limit expiry logic through \texttt{computeEffectiveStatus} before returning the result.

\begin{lstlisting}[
  caption={\texttt{getEffectivePermissions} (\texttt{helpers.ts}). Resolves the live permission state for any photo message by looking up the canonical record in \texttt{mainMessages} and applying expiry logic.},
  label={lst:get-effective},
  language={}
]
export function getEffectivePermissions(
  mainMessages: ChatMessage[],
  message: PhotoMessage,
): PhotoPermissions {
  const raw = mainMessages.find(
    (entry): entry is PhotoMessage =>
      entry.type === "photo"
      && entry.sourcePhotoId === message.sourcePhotoId,
  )?.permissions ?? message.permissions;

  const expiresAt = raw.expiresAt ?? null;
  const now = Date.now();
  return {
    ...raw,
    expiresAt,
    status: computeEffectiveStatus(raw.status, expiresAt, now),
  };
}
\end{lstlisting}

This derivation pattern means that a single state update to the canonical photo in \texttt{mainMessages} is sufficient for every participant view---sender, recipient, forwarded recipient, and co-subject---to reflect the change on the next render cycle. The prototype does not need to synchronise permission records across message arrays or maintain separate update logic for forwarded copies, because every component derives its view of permissions from the same canonical source.

\subsection*{Local Interaction State}

Alongside the shared permission state described above, \texttt{PhotoRevocationDemo} maintains a second category of state: transient values that control temporary interface behaviour rather than the canonical permission model. These include boolean flags that govern which overlay is currently visible (\texttt{pickerOpen}, \texttt{composerOpen}, \texttt{timeLimitModalOpen}), a structured value tracking which photo menu is active and in which mode (\texttt{openPhotoMenu}), and draft text fields that hold in-progress user input before it is committed (\texttt{draftCaption}, \texttt{accessRequestDraft}, \texttt{senderInput}, \texttt{recipientInput}). None of these values affect how permissions are stored or derived; they exist only to support the interactive surface of each handset view.

One notable piece of local state is the countdown tick. The prototype supports time-limited photo access, and the remaining time must update visually every second. Rather than introducing a timer event system, the orchestrator increments a counter once per second via a \texttt{useEffect} hook:

\begin{lstlisting}[
  caption={Countdown tick effect in \texttt{PhotoRevocationDemo.tsx}. The tick value itself is never read; its sole purpose is to force React re-renders.},
  label={lst:countdown-tick},
  language={}
]
const [, setCountdownTick] = useState(0);

useEffect(() => {
  const id = setInterval(() => setCountdownTick((t) => t + 1), 1000);
  return () => clearInterval(id);
}, []);
\end{lstlisting}

\noindent
The tick value is never read directly---the destructured state variable is deliberately discarded. Its only purpose is to trigger a React re-render every second so that \texttt{getEffectivePermissions} (Listing~\ref{lst:get-effective}) and \texttt{formatExpiryCountdown} re-evaluate with a fresh \texttt{Date.now()}. This allows time-limited photos to expire visually in real time and countdown labels to update continuously, without requiring explicit expiry event handling or additional state-management infrastructure.

Separating these transient interaction values from the canonical permission state kept the implementation manageable: the permission model remained a clean, single-source-of-truth structure as described in the previous subsection, while the local state layer provided the flexibility needed to support rich interactions such as modal sequencing, draft composition, and live countdown display.

\subsection*{State Transitions: Revocation and Forwarding}

The two most consequential state transitions in the prototype are post-send revocation and constrained forwarding. Both operate on the canonical--copy architecture described in Section~\ref{sec:components-state}, but they update state in different directions: revocation modifies the canonical record so that all views change, while forwarding reads the canonical record to decide whether a new copy may be created.

\subsubsection*{Post-Send Revocation}

When the sender revokes access, the handler \texttt{updateSelectedPhotoPermissions} is called with a partial update---for example, \texttt{\{~status:~"revoked"~\}}. This function maps over \texttt{mainMessages}, locates every entry whose \texttt{sourcePhotoId} matches the currently selected photo, and merges the update into its \texttt{permissions} object:

\begin{lstlisting}[
  caption={\texttt{updateSelectedPhotoPermissions} in \texttt{PhotoRevocationDemo.tsx}. The immutable map-and-merge pattern updates the canonical record without mutating existing state.},
  label={lst:update-permissions},
  language={}
]
const updateSelectedPhotoPermissions =
  (updates: Partial<PhotoPermissions>) => {
    if (selectedPhotoId === null) return;
    setMainMessages((currentMessages) =>
      currentMessages.map((message) => {
        if (message.type !== "photo"
            || message.sourcePhotoId !== selectedPhotoId)
          return message;
        return {
          ...message,
          permissions: { ...message.permissions, ...updates },
        };
      }),
    );
  };
\end{lstlisting}

\noindent
Because \texttt{forwardedMessages} is never rewritten, the revocation takes effect across all participant views through the derivation layer already shown in Listing~\ref{lst:get-effective}: on the next render cycle, every \texttt{PhotoMessageBubble} calls \texttt{getEffectivePermissions}, which looks up the now-revoked canonical record and returns \texttt{"revoked"} as the effective status. The same handler is reused for restoring access, toggling the download flag, or enabling the co-subject flag---each is simply a different partial update passed to the same function.

\subsubsection*{Constrained Forwarding}

Forwarding introduces a new message into \texttt{forwardedMessages}, but only after checking the canonical permission state. Listing~\ref{lst:forward-photo} shows the handler:

\begin{lstlisting}[
  caption={\texttt{forwardPhotoMessage} in \texttt{PhotoRevocationDemo.tsx}. The function guards on effective permissions before creating a linked copy.},
  label={lst:forward-photo},
  language={}
]
const forwardPhotoMessage = (message: PhotoMessage) => {
  const effectivePermissions =
    getEffectivePermissions(mainMessages, message);

  if (effectivePermissions.status !== "active"
      || !effectivePermissions.canForward) {
    return;
  }

  const forwardedMessage: PhotoMessage = {
    id: getNextMessageId(mainMessages, forwardedMessages,
      senderOnlyMessages, coSubjectOnlyMessages,
      recipientOnlyMessages),
    sender: "recipient",
    type: "photo",
    assets: [...message.assets],
    caption: `Forwarded: ${message.caption}`,
    time: getTimeLabel(),
    permissions: effectivePermissions,
    sourcePhotoId: message.sourcePhotoId,
  };

  setForwardedMessages((prev) => [...prev, forwardedMessage]);
};
\end{lstlisting}

\noindent
Two details are significant. First, the guard clause calls \texttt{getEffectivePermissions} to evaluate the canonical record at the moment of forwarding; if the photo has been revoked or its \texttt{canForward} flag is \texttt{false}, the function returns early and no copy is created. Second, the forwarded message carries the same \texttt{sourcePhotoId} as the original. This means that if the sender later revokes access, the derivation layer will resolve the forwarded copy against the updated canonical record, and the forwarded recipient's view will reflect the revocation without any additional update to \texttt{forwardedMessages}.

\subsubsection*{Time-Limit Expiry}

Time-limited access follows the same derivation principle without requiring a dedicated state transition. When the sender configures a time limit before sending, the photo message is created with an \texttt{expiresAt} timestamp. No handler fires when the deadline passes; instead, \texttt{computeEffectiveStatus} (called within \texttt{getEffectivePermissions}) compares \texttt{expiresAt} against \texttt{Date.now()} on every render and returns \texttt{"revoked"} once the timestamp has elapsed:

\begin{lstlisting}[
  caption={\texttt{computeEffectiveStatus} in \texttt{photoModel.ts}. Expiry is treated as implicit revocation---no event or state write is needed.},
  label={lst:compute-status},
  language={}
]
export function computeEffectiveStatus(
  storedStatus: PermissionStatus,
  expiresAt: number | null,
  nowMs: number,
): PermissionStatus {
  if (storedStatus === "revoked") return "revoked";
  if (expiresAt != null && nowMs >= expiresAt) return "revoked";
  return "active";
}
\end{lstlisting}

\noindent
Combined with the countdown tick described in the previous subsection, this ensures that a time-limited photo transitions smoothly from an active countdown display to a revoked placeholder at the moment of expiry, using the same rendering path as an explicit revocation. This uniformity---where manual revocation, forwarding constraints, and time-limit expiry all resolve through a single derivation function---operationalises the dissertation's treatment of consent as ongoing and revisable: a single state change at the source, whether made by the sender or by the passage of time, is sufficient to update every downstream presentation of the photo.

The result of any change is visible immediately in the chat thread. As shown in Figure~\ref{fig:permission-chips}, each photo message carries a collapsible summary row beneath the bubble. \subsection*{Recipient Experience and Revoked States}

The recipient's view mirrors the sender's permission chips but does not expose any management controls. \subsection*{Forwarding and Access Requests}

Forwarding is gated by the canonical permission state. When \texttt{canForward} is \texttt{true} and the photo is active, the recipient's action menu enables \emph{Forward}; the handler \texttt{forwardPhotoMessage} (Listing~\ref{lst:forward-photo}) checks \texttt{getEffectivePermissions} at the moment of forwarding and, if permitted, appends a new message to \texttt{forwardedMessages} with the same \texttt{sourcePhotoId}. The forwarded copy therefore remains linked to the canonical record: any later revocation by the sender propagates to both the recipient and the secondary recipient without additional synchronisation, as described in Section~\ref{sec:components-state}.

Figure~\ref{fig:forward-revoke-request} shows the prototype after the sender has revoked access to a previously forwarded photo. All three handsets reflect the change simultaneously: the sender's view retains the photo but displays a revoked summary; the recipient's bubble is replaced by the ``Access changed'' placeholder with \emph{Forward} and \emph{Download} disabled in the action menu; the secondary recipient's forwarded copy shows the same revoked placeholder and chips (\emph{Revoked}, \emph{No forwarding}, \emph{Not reviewable}, \emph{Download blocked}). The recipient's menu now includes \emph{Request access} as the only actionable option beyond \emph{Reply}.

\section{Software Testing}\label{sec:software-testing}

\subsection*{Manual Cross-View Verification}

After each substantive change, the prototype was exercised manually in the browser across all four stakeholder views (sender, recipient, forwarded recipient, and co-subject). These manual checks concentrated on cross-view consistency: confirming that a revocation performed in the sender panel was immediately reflected in the recipient and forwarded-recipient panels, that permission chips updated accordingly, and that warning text remained visible where expected. Manual verification was particularly important for visual and layout details---such as colour-coded status indicators, animation transitions, and responsive scaling---that automated tests running in a simulated DOM environment cannot fully capture. Version control was maintained with Git throughout both development phases, providing a traceable history of changes and the ability to isolate regressions.

\subsection*{Automated Unit and Component Tests}

To supplement manual checks, an automated test suite was developed using the tooling listed in Table~\ref{tab:tech-summary}: Vitest as the test runner, React Testing Library (RTL) for component rendering, and jsdom as the simulated browser environment. RTL's design philosophy prioritises testing components through their user-facing behaviour---querying by accessible roles, labels, and visible text rather than internal implementation details. % TODO: You may optionally cite RTL's guiding principle here if you add the reference.
This aligns well with the prototype's goals, since the critical question is whether a user would see the correct permission state, not whether a particular internal variable holds the expected value.

The test suite, located under a dedicated \texttt{tests/} directory, is organised into three layers. \emph{Unit tests} verify pure helper functions and the permission model in isolation: for example, confirming that \texttt{computeEffectiveStatus} treats a past expiry as revoked regardless of the stored status, or that \texttt{getEffectivePermissions} falls back to the message's own permissions when the canonical source is absent from the main thread. \emph{Component tests} render individual UI elements (the photo bubble, composer, picker, time-limit modal, request panels, and text message bubble) within a lightweight harness that supplies controlled props. These tests exercise specific branches: a revoked photo displaying the ``Access changed'' placeholder, a view-once photo transitioning to ``Opened once'' after consumption, the download button being disabled when \texttt{canDownload} is false, and the co-subject depicted-person card reflecting both the active and revoked states. \emph{Integration-style tests} render the full \texttt{PhotoRevocationDemo} orchestrator and simulate multi-step user journeys spanning several handset panels: revoking a photo and observing the recipient subtitle change, forwarding a photo and verifying it appears on the secondary handset, sending and then accepting or rejecting access and revocation requests, and consuming a view-once photo through the modal lifecycle.

Edge cases are tested alongside the primary flows. These include restoring access on an already-expired time limit (which must also clear the \texttt{expiresAt} field), sending an empty text message (which should produce no new entry), cancelling the time-limit modal without applying an expiry, and verifying that permission-detail chips display the correct label variants---``View once unavailable'' versus ``Not reviewable''---depending on whether the underlying policy was view-once. Coverage is collected using \texttt{@vitest/coverage-v8}; at the time of writing the suite comprises over one hundred assertions and achieves statement coverage above ninety per cent for the included source files, with an eighty per cent function-coverage threshold enforced in the Vitest configuration.

\subsection*{Scope and Limitations}

The automated suite operates within jsdom, which faithfully reproduces DOM structure but does not execute real CSS rendering, browser-specific layout, or navigation. No end-to-end browser automation framework such as Playwright or Cypress was introduced: the additional infrastructure cost was not justified for a single-page, single-user prototype where all views coexist in one render tree. Similarly, because the prototype has no backend, there are no API or database tests. These boundaries are consistent with the project's scope as an interactive proof-of-concept for evaluating the Smart Photos permission model, rather than a production messaging system. Automated tests therefore serve as a regression safety net for the permission logic and UI behaviour, while the broader question of whether users understand and trust that behaviour is addressed through the qualitative evaluation in Chapter~6.
